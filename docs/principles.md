# 设计原则

纸鸢的产品与界面取舍，沿用下面这几条。每条后面是理由和出处，改动前先对照。

## 1. 简化以长期深度使用为前提

只去掉重复信息和完全无用的入口；削减能力、大重构一律暂缓。
理由：纸鸢是天天开着用的驾驶舱，用户依赖的是能力的完整，砍功能换来的"干净"不值得。（D-238）

## 2. 所有审批走同一个右侧抽屉

需求、决策、验收、状态申请都在同一个右侧抽屉里处理，不再各开弹窗或另起页面。
理由：同一类动作只有一种手感，用户不用重新学习，也不会漏掉藏在别处的待办。（R-177）
例外：触屏上「要你处理」等列表里，验收和批准类决策可以左滑一条露出「通过 / 退回」，再点一下才执行；同样走第 8 条的撤销期，退回要先写意见（第 9 条的草稿）。这是用户在 D-491 明确选择的（R-73）；选项类、多点决策和其它审批仍只在抽屉里做。

## 3. 列表和工作台只放固定高度的条目

列表、泳道、工作台里的条目高度固定，长内容截断（截断时才弹全文提示），详情进抽屉看。
理由：高度不跳，扫读才快；信息密度靠抽屉承接，不靠撑开卡片。（R-177、R-186）

## 4. 离开时间不固定，不用「早报 / 明早」这类说法

文案、提示词、界面里都不预设用户几点离开、几点回来，用「回来时」「离开期间」之类中性说法。
理由：用户的作息不固定，写死时段会误导，也会让汇报节奏对不上。（R-165）

## 5. 同一信息只在一处表达

同一个状态、标题、数量不在同一视图里重复出现（行里已写标题，引用小标就不再弹提示）。
理由：重复信息要么多余要么互相矛盾，且占掉本可以给别的信息的空间。（D-238、R-186）

## 6. 界面类改动交验收要用真实数据截图，且新旧证据格式都覆盖

截图来自真实数据而不是造的样例；需求抽屉里同时有结构化证据和老格式证据（一段文字加几张截图，多数需求是这种），两种都要截到。
纸鸢自己的做法：用 `sqlite3 ~/.kitestring/hub.db ".backup /tmp/kxx/hub.db"` 复制一份只读快照，在演示 hub 里打开真实需求截图；演示 hub 用独立端口和 /tmp 下的短路径；录屏 deviceScaleFactor 用 1。
理由：只验新格式会让老需求的证据显示悄悄坏掉，这类问题已出现过。（R-181、R-185）

## 7. 部署一律走脚本

用 `scripts/deploy.sh`（或 `make deploy`），不手工拷二进制、不手工重启服务。
理由：脚本固定了构建顺序、备份、先 rm 再 cp 替换（macOS 直接覆盖正在运行的程序会被 SIGKILL）、部署后核对和失败回滚。（R-194）

## 8. 撤销期不挡用户的下一步，但系统替用户做的下一步要等它结束

撤销期是为了误操作时能马上取消，不能挡住用户自己的下一步操作。操作后结果立刻到位，在元素上给进度和撤回；用户可以马上继续做别的（连续审批时按 → / J / 下一件立刻翻走，不用等）；元素离开屏幕后，撤回挪到顶部浮动条。不锁界面，不排队等待。
系统替用户做的下一步（连续审批的自动翻到下一件）不一样：它要等撤销期走完再做——通过 / 退回后停在这一件、盖着撤销遮罩，3 秒生效后才自动翻页；撤销期内点撤回，恢复原状、不翻；用户自己先翻走了，这次自动跳转随之取消，不会多翻一件。（R-226，改写 R-201 / R-195 / R-177 的「盖章后立刻翻」）
全站只有一套撤销机制（`web/src/app/verdict.tsx` 的 `schedule`，3 秒，D-229）：验收、决策、计划 / 阶段、改需求状态、开始计划、撤销授权、撤回放行都用它，撤销条只有一种样式（R-218：半透明遮罩 + 原句「3 秒后改为待开始」+ 右侧满高的撤回按钮和倒计时圆环；行内 / 盖在块上 / 顶部浮动三种摆法），进度按操作那一刻的真实时间走，换列、翻页、重新渲染都不重来；批量操作只出一条汇总；需求换列和撤回、失败回滚用同一套换列动画（R-200）。新增有等待期的操作也接这套，不另写。
理由：用户要求类似操作都保持一致。（用户 2026-10-24，R-201）

## 9. 输入的内容不因关闭、翻页、刷新而丢失

有输入框的地方（新建 / 编辑需求、验收与审批意见、留言、回复、退回 / 搁置原因、计划）写到一半的内容存为本机草稿：关抽屉、翻到下一件、刷新、手机下拉关闭后回来，文字和贴图都还在，旁边一行小字「已恢复上次没写完的内容 · 清空」，所以关闭时不再弹确认。
全站只有一套（`web/src/app/draft.tsx` 的 `useDraft`）：只存在本机浏览器，单段文字上限约 2 万字、贴图只存已上传文件的引用、总量约 1MB 超出先清最久没动的；提交成功才清（撤销期内撤回时还在），对象关闭（已完成 / 已答复 / 已搁置）后自动清，7 天没动的清；「清空」立即清掉文字和贴图并删除草稿，不走撤销期；编辑已有内容时另有「恢复原文」，走第 8 条的撤销期；有草稿的条目标「草稿」。设置页、搜索、⌘K、标注文字框不存。新增输入框也接这套，不另写。
理由：误关或切走去看别的信息后回来要重写一遍，代价都落在用户身上。（用户 2026-10-24，R-202）

## 10. 原型只是参考，成品不带过程痕迹

原型里的设计说明、图例解释、「推荐」「原型说明」「真实数据：…」脚注、需求 / 决策编号注释、演示用的切换按钮（方案 A/B/C、宽度、回放）、「点这里试试」之类的引导语，都只是给用户看方案用的，成品里一律不出现；成品只保留用户使用时真正需要的文字。拿不准某段文字该不该留，问主助理。主助理做原型时，把说明放进明显分开的「设计说明（不进成品）」区域，和界面本身分开。派界面类需求与交验收前，PM / Dev 自查截图里有没有原型说明残留。
理由：做出来的界面就是成品，过程痕迹留在里面是噪音，还要用户自己看出来。（用户 2026-10-24，R-213）

## 11. 状态和标记只来自明确的记录，猜出来的内容必须标明是猜的

会让用户停下来处理、或决定通过 / 拒绝的状态和标记——「要你处理」、泳道上的「等你」、批准 / 拒绝、推荐哪个选项、在等你回答还是等你授权——只认明确的记录：会话提了决策、交了验收、请求了授权、用 AskUserQuestion 这类提问工具在问；用户点的是批准还是拒绝、提问方标的是哪个推荐选项，都在发生时存成字段。不再从对话文字里用关键词、问号、开头几个字、模糊匹配去猜；对话里写的问句不进「要你处理」，关键词判断只用来提醒会话本身「你像是在问用户，请提决策」。模型摘要、推测的原因、估计这类猜出来的内容可以显示，但要写明是推测，不能画成状态标记。
理由：靠猜的标记时对时错，报告进度被当成在问你、真在问又漏掉，用户没法信任界面上的状态。（用户 2026-10-24，D-729，R-239）
